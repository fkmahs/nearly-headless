# nearly-headless

**Run a team of coding agents the way a product manager runs a team.** You talk to one supervisor per list of work, in plain words, from your laptop or your phone. It keeps the list, starts a background builder for each change, and comes back only for what needs your yes: a merge, a release, a message to someone else. Every change ends in one pull request, which is its record; every list lives in its repo, so any laptop picks up where another left off.

- **Supervisors** keep one list each: plain names, a note per piece with its brief, your decisions and where it stands. They merge on your yes, release from main, and tidy up after.
- **Builders** do one piece each, in their own worktree: a draft PR first, the repo's own checks in a Linux container in minutes, turns on shared test environments, then CI as the proof.
- **The command center** (`nh serve`) shows every repo's work as one tree: what waits on you, what is building, what is queued and why.
- **Guards, not hopes:** gates that refuse a merge that wasn't tested against the latest main, a check that flags anything off the rules, a reply check that holds supervisors to your format, and a privacy guard that stops private names reaching a public repo.

It works with Claude and Codex, on Windows, macOS and Linux. Identical on every laptop; only one small settings file differs. MIT licensed.

## Set up a laptop

Follow the **[New laptop checklist](docs/new-laptop.md)**: the tools and sign-ins, the Claude app settings, `nh setup`, each repo's secrets, then `nh doctor` and `nh serve`. It is written for Windows; elsewhere, `bin/nh` stands in for `bin\nh.cmd`. A laptop that only uses nearly-headless (no changes to it) clones it over https with no GitHub login: see [a read-only laptop](docs/new-laptop.md#a-read-only-laptop).

It stays current by itself: once a day, the first `nh` command checks GitHub and moves to the newest release, which then installs itself. Releases exist only after the owner's yes. `nh update` does it now; `auto_update = false` in the settings file turns it off.

It works with Claude and Codex: setup installs the skills and the owner's expectations for each agent it finds on the laptop.

## What it gives you

| | |
|---|---|
| `nh serve` | the command center: your work as a tree (repo, its supervisors, and under each what waits on you, what is building, queued (and why each waits), to do and to fix, parked work), every item's details in a pop-up, repos and pull requests, a nearly-headless page with every part of nearly-headless and how they connect (a map of the roles and steps, drawn as steps in order on a phone; the hooks setup installs and whether each is on; who does what, each with the text of its skill or `wk` command; the settings this laptop sets; tap any part for its details; all read from what is installed and configured, `wk/system.py`), whether nearly-headless is current, and a Tokens & cost tab (cost this week against last, by role, repo and model at API list prices, with the token counts in a details section; 2, 4, 8 or 13 weeks, two by default). Check GitHub now shows its progress and updates the page when the fresh view is ready. It restarts on a new nearly-headless release by itself. `--save FILE` writes it once, to share |
| `nh product / piece / question / order` | a supervisor's list (a `product`: one per supervisor, with the invoice line `product set --line` changes, and any named extra lines `--line fixes="..."` adds, so one list can bill as several invoice rows), its pieces (a plain name, PR, builder and a note that is the piece's memory), your questions and standing orders, in the repo's `.work/`. `piece queue` records the ordered queue you approved at a check-in (to-do pieces with their brief and the files they touch, `piece set --files ... --after P3`); `piece next` says which start now and why the others wait: at most `builders_per_list` builders per list when the settings file sets it, else no limit (one waiting on a merge doesn't count), never on files an open PR, a turn or a piece being built holds, never before the pieces it comes after merge. The supervisor starts them whenever a builder hands back or a merge starts waiting; nothing in it merges, deploys or releases. `question withdraw --reason` takes back a question the supervisor can decide itself (a reversible step inside the agreed scope), noted in its piece's note (a whole-list question names one with `--piece`) as its call, not yours |
| `nh check [repo] [product]` | read-only: each list against GitHub and the rules (piece vs PR and branch, states, names, notes, questions, hours, billing, leftover branches, code on main without a PR, files that don't belong in GitHub, a supervisor chat or builder that went past Claude's compact window (`autoCompactWindow`) in the last 2 days, read from Claude's own chat records; and the setup's health: tests failing on the base branch or on a PR waiting for the owner's yes, committed files that look like they hold a key, token or password (file and line only), to-dos untouched for 30 days, instruction files over their word budget (`WORD_BUDGET` in `wk/check.py`), look-alike open pieces), one line per problem with the command that fixes it; `--json` too. Supervisors run it on start and before every catch-up; the command center shows the count per list. `--fix` makes only the mechanical fixes, through wk's usual writes, one line per change: a piece still ready or building after all its PRs merged becomes merged, a piece's branch that exists neither on GitHub nor here is cleared, and a builder's local `worktree-agent-*` branch with nothing off main, whose folder is gone, is deleted with `git branch -d` (an unmerged one is kept); it never deletes a remote branch, rewrites a note, touches a question or changes code, and lists everything else as before; `--fix --dry-run` only says what it would change. wk refuses at write time what the check would flag: a note line over 600 characters (`nh piece note --add`, or any line of a `--file`), a piece name over eight words or with a ticket number or file name (`nh piece add`, `set --name`). `--fix-dates` tidies one list's note dates once; `--ack <sha>` records that the owner has looked at a commit that came without a PR, `--ack branch:<name>` a branch he keeps, `--ack file:<path>` a tracked file he allows, `--ack secret:<path>` a file whose possible secret is not one. Repo-wide lines are for one list only: the project manager's calls list, else the repo's only list |
| `nh health [--days N]` | read-only: is the system healthier on tokens? One short table over every Claude Code transcript on this laptop (chats and their agents), for today so far, yesterday, this week, last week and the previous N full days (default 14), every figure per day (today counts as the part of it gone): API calls; fresh input, cache write, cache read and output tokens; context per call (p50, p90) for chats and for agents; agent runs, wake-ups (a run after an agent's first) as a share of runs, median tokens and minutes per run; merged PRs, reviews per merged PR, and agent tokens per merged PR where its builder can be tied to it ("unknown" where it can't); reply-check rejections; `nh refresh` uses and refusals. Each period shows the nearly-headless versions live in it (from the `vX.Y.Z` tag dates), and each measure says which way is healthier and its verdict, this week against last week: healthier, worse or flat (within 10%), with a list of what got worse. `--json` gives every period, its verdicts against the period before and the version live each day. Message text is never read beyond the markers it counts; each transcript is kept by size and change time in a cache file in the temp folder, so a rerun takes seconds. Supervisors run it when you ask how the system is doing, and add your plan usage from the app |
| `nh hours` | hours you state, per product, in the repo's `.work/hours.tsv`, naming the pieces they pay for (`--for`) and, optionally, the list's named invoice line they bill on (`--line-key`); `fix` corrects an unbilled entry, its line key too; `mark` labels them done (an invoice, a timesheet) for toolkits |
| `nh channels` | a client's channels file (`.work/communication_channels.md`): where its work is talked about and how to read each place, in the client repo's own words; shows each channel's last-checked time on this laptop, and `--checked` with `--at` moves one (local state, never committed, never into the future) |
| `nh inbox` | each list's inbox (`.work/<list>/inbox.md`): client messages routed to its supervisor, a link and one line each, never their text; `add` refuses a link already filed in the repo, `check` asks, `done` removes a handled one. The command center shows each list's unread count. One scheduled routing run fills them every 30 minutes in working hours ([`skills/supervisor/routing.md`](skills/supervisor/routing.md)); nothing is ever sent |
| `nh turn / gate` | taking turns on shared test environments; release, approval and merge (latest main) gates |
| `nh test [modules] [--plan] [--full] [--local]` | a builder's local proof in minutes: reads the repo's change → check map (`## Change → check` in AGENTS.md or CONTRIBUTING.md), matches every file the branch changed against origin/main (committed or not) and runs each mapped command once; the full-run row or a file no row names prints "full run needed" and exits 1, since CI runs the whole suite. Named unittest modules, or `--full` (the map's full-run row), run just those. On Windows or macOS, in a repo with a `wk-test.Dockerfile`, the checks run only in a Linux container, many times faster: if Docker is off, wk starts Docker Desktop and waits; if it can't, no checks run and it exits 4 with one line naming what is needed (5 if the Linux image won't build). `--local` runs them on the laptop |
| `nh refresh --pr N` | brings a stale PR up to date with no builder: merges main in its builder's worktree; clean, it pushes, waits for CI, posts `Ready @ <sha>` and prints the sha; a conflict, a change needing the full run, or a latest Ready that isn't `Gap checks: none` changes nothing and says the builder is needed. Run it before `nh gate fresh` |
| `nh recall` | a supervisor's list as it stands, in one block of about 4,000 characters at most (questions, pieces with builder, PR state and CI, newest note and decision lines, the list's `nh check` findings that need no network (to fix, those needing the owner's yes marked), turns, the approved queue with what starts now and why each other piece waits, inbox, standing orders), which Claude puts in the chat when it starts or resumes and after compacting or clearing it (setup installs the hooks) |
| `nh reply-check` | sends a supervisor back, once, when its reply lacks a part you require, or when its turn drafted a message, investigated or reviewed a document for you and recorded none of it as a piece (setup installs the hook; required parts are off until you list them, the record check is on until `record = false`, see [new-laptop](docs/new-laptop.md#checking-supervisor-replies)); `--remind` names those parts in one line before each turn, so the reply is right the first time |
| `nh setup --repo "name=path,url=..."` | adds a repo to this laptop: into the settings file beside what is there, cloned if missing |
| `nh doctor / update / version` | keeping the laptop right and current (off Linux, a missing or stopped Docker is a failure: builders' tests need it) |

## Skills

Setup and `nh update` install each one in `skills/`.

| | |
|---|---|
| supervisor | runs one list of work with the owner: its pieces, one builder per code change (checks, short investigations and approved data fixes it does itself or with a small query-first agent), two fresh reviews (Opus on the PR, then Sonnet on the fix), merges on the owner's yes, hours; goes ahead with reversible steps inside a piece's agreed scope and reports them instead of asking, withdrawing on every start the questions it can now decide; starts the owner's approved queue as builders free up; reads its inbox on every start, and drafts replies to client messages as questions for the owner to send himself |
| builder | does one piece: one PR, or one written finding, then stops; proves with data before the browser and with the map's checks (`nh test`) before CI, posts `Progress:` lines, marks claims checked or inferred |
| catch-up | one table of every open piece on a list, in the recommended order |
| project-manager | one per client, on top of supervisor: owns the calls list and call hours, turns call notes into pieces on the right lists, takes the client messages no list could, runs the Friday invoice |
| wwid | predicts how the owner would answer, from the WWID profile repo (optional, see below) |

`AGENTS.md` holds the owner's expectations; setup puts them in `~/.claude/CLAUDE.md` (Claude) and `~/.codex/AGENTS.md` (Codex), so every chat on the laptop reads them, in every repo. Claude's copy also carries `templates/compact-instructions.md` (what Claude keeps when it compacts a chat: open pieces, waiting decisions, running builders with their agent ids, this turn's work); if you keep your own `~/.claude/CLAUDE.md`, copy that section into it. Setup also adds to `~/.claude/settings.json`, beside whatever is there: a `SessionStart` hook for `startup`, `resume`, `compact` and `clear` that runs `nh recall`, a `Stop` hook that runs `nh reply-check`, a `UserPromptSubmit` hook that runs `nh reply-check --remind`, and `"autoCompactWindow": 256000`, so no chat grows past 256K tokens before Claude compacts it (Claude's own default lets a chat run toward 1M, re-reading all of it every turn; a window you set yourself is kept); `skills/` the supervisor and builder, and `templates/` the PR template, a CI workflow `nh doctor` checks against, and the channels file `nh channels` starts from.

**Only code goes to GitHub.** Spreadsheets, client documents, archives and Office lock files (`*.xlsx *.xls *.xlsm *.xlsb *.csv *.pdf *.docx *.doc *.pptx *.zip ~$*`, one list in `wk/keepout.py`) stay on the laptop: setup adds them to each listed repo's local git exclude file (`.git/info/exclude`, shared by its worktrees, never committed) in a marked block, leaving your own lines alone, and `nh doctor` reports it. `nh check` flags, repo-wide, any such file already on the base branch, and any other binary file (as git counts it) outside `docs/`, where design images belong, each with the `git rm --cached` command that takes it out of git and keeps your copy. Nothing is deleted. Images that deliberate visual tests use (snapshots, say) are acceptable but not preferred: allow each file explicitly with `nh check <repo> --ack file:<path> --reason "..."`. Anything else binary stays out. One exception is built in, in the check only: statements of invoices the invoicing toolkit made before 1.30 (`billing/*.csv`), already in git and never rewritten; since 1.30 an invoice's statement is its readable `billing/<ID>.md` alone.

**A list can live apart from its code.** A repo's `.work/` is in its own checkout unless its settings entry names another: `list = "<folder>"` (and `list_base`, default main). Then every list command, the command center, `nh check`, the hooks and recall read and record the list there, while PRs, CI, turns and gates use the code checkout. That is how a public repo keeps its list in a private one.

**Private names stay private.** A repo marked `public = true` in the settings gets the privacy guard (`nh privacy`, `wk/privacy.py`). The private name list is built on the laptop and never written to a repo: every repo's name, folder and client in the settings, the owner's names, and `[privacy] terms = ["..."]` for anything else (an employer, people, tickets). `nh setup` installs a pre-push hook in each public checkout that stops a push whose branch name, commit messages or added lines hold one, naming the file and line, never the name; the CI job `privacy` checks a PR's title, description and commits against the repo secret `PRIVATE_TERMS` (`nh privacy secret <owner/repo>` sets it), and `nh gate fresh` checks a public PR's title, description and comments at merge. `nh privacy tree <folder>` builds a repo's clean public copy (every file on main except `.work/`) and scans it. Every PR, public or not, has four headings, What was wrong, What changed, How it was tested, What it means for you (`.github/pull_request_template.md`); `nh gate fresh` refuses one opened without them since the laptop took the rule up (`pr_sections_from`, set by setup) and warns about older ones.

**`nh` runs one kit.** `nh setup` records the checkout it ran from as `kit` in the settings; `bin/nh` and `bin\nh.cmd` (and the older `wk` names, which still work) in any other checkout (the one on your PATH, say) forward to it, so moving the kit never means changing PATH. `nh doctor`'s first lines say which checkout ran, and the forwarder it came through. Running setup from another checkout moves `kit` there, which is also the way back.

**nearly-headless holds nothing personal and no client's data.** The WWID profile (how they decide, and their verdicts on the wwid skill's predictions) lives in its own private repo beside nearly-headless: `wwid_profile = "<folder>"` in the laptop's settings file names it, and the wwid skill reads it and records verdicts there, written without client names. It is optional: without it the wwid skill says it is off, the reply check asks only for the parts `[reply] require` lists, and `nh doctor` shows "WWID profile: not set (optional)". `nh setup --profile <folder>` adds it, with the reply check's "What would I do" mark; setup also adds a `wwid` checkout it finds beside nearly-headless, and takes the mark out on a laptop without a profile. So nearly-headless can be copied to any laptop, or a company's GitHub, as it is.
